What the main project demonstrates

Real services

Browser UI, two venue services, two coordinators and MongoDB communicate over HTTP and TCP in Docker Compose or Kubernetes.

Implemented algorithms

Bully leader election, Lamport logical clocks, Berkeley physical clock synchronization, and atomic per-seat MongoDB updates.

Limits

Two coordinators are a demo, not quorum consensus. Venue event history and coordinator clocks are in memory. A single MongoDB instance is persistent but not highly available.

Synchronization and distributed computation

Lamport and vector clocks

Make local events or send/deliver messages between processes. Lamport order captures causality only as “happened before”; vector clocks can distinguish concurrent events.

Global state / snapshot

A distributed snapshot records process states plus messages in transit. It is not the same as reading all machines at one wall-clock instant.

No snapshot recorded.

Physical clock synchronization

Berkeley-style coordinator averages offsets and asks nodes to adjust. The booking system implements a simplified version; wall clocks are never perfectly synchronized.

Offsets (s):
Enter offsets relative to the coordinator.

Model of distributed computations: represent each process as an event sequence; communication edges connect send and receive events. A valid global ordering is a topological ordering that preserves every process order and every message’s send-before-receive relation. Virtualization and containers package processes and their dependencies, improving isolation and repeatability but not removing network or storage failures.

Architectures, design issues and emerging paradigms

Types, architectures and middleware

Centralized client-server, multi-tier, peer-to-peer and hybrid systems differ in control and failure patterns. Middleware offers common APIs for messaging, naming, serialization, discovery and security. Design issues include partial failure, latency, consistency, replication, concurrency, security and observability.

Distributed multimedia systems

Audio/video systems need timely delivery, synchronization of media streams, jitter buffering, adaptive quality and often tolerate some loss rather than waiting for late data. This project has no media pipeline; its WebRTC exercise is a data channel only.

Fault tolerance

Replication, retries, timeouts, health checks and leader election help handle faults. Retries need idempotency; partitions can create split brain. The demo uses leader failover but has no quorum consensus or replicated database.

Distributed object- and web-based systems

Remote objects expose methods through proxies/stubs; REST/HTTP exposes resources and representations. SeatSync uses HTTP JSON endpoints and a browser client; the coordinator-to-venue request is RPC-like.

Distributed file systems

HDFS divides files into blocks and replicates them across data nodes with a name service. The optional Hadoop cluster in this repository demonstrates HDFS/YARN for a MapReduce word-count job, not a general-purpose shared filesystem for booking data.

Serverless architectures

Functions run in provider-managed, event-triggered environments with scaling and billing by execution. No serverless deployment is included; the venue/coordinator services are long-running containers.

Blockchain and distributed ledgers

Replicated append-only records are agreed using consensus. Immutability and auditability trade off throughput, latency, privacy and governance. A ledger is unnecessary for this single-operator booking database, so no blockchain is implemented.

Distributed database trade-offs

Replication improves availability but adds consistency and conflict choices. Partitioning distributes load but complicates queries and transactions. SeatSync uses one MongoDB service and atomic per-seat updates; it does not demonstrate a multi-node database or CAP behavior under partition.

Case studies

Megaport: cloud networking and service orchestration. Cloudflare: globally distributed edge services. AWS: cloud primitives and managed services. Apache Hadoop: distributed storage and batch processing. Kubernetes: container orchestration, scheduling and self-healing. These names are study references; SeatSync deploys locally and does not integrate with these providers.

Self-study: Lodha–Kshemkalyani and Knapp

Lodha–Kshemkalyani describes a fair distributed mutual-exclusion algorithm; review its ordering and fairness proof separately from the educational queue above. Knapp's classification organizes distributed deadlock-detection approaches (for example, centralized, hierarchical and distributed detection) and their communication/phantom-deadlock trade-offs. This app provides a wait-for-graph exercise, not those full algorithms.
